# Bidirectional Log

A Bidirectional Log records execution as a two-way log, persisting one commit
for each step. When traversing forward, the system performs normal execution.
When traversing backward, it performs a rollback by first issuing a git-style
revert of the persisted state and then replaying each step's receipt through
the owning tool's Undo method. The pattern comprises a typed checkpoint port,
Dolt-backed history, receipt-driven undo, a two-part rollback mechanism, and
an explicit story for irreversible tools.

## Intent

The intent is to record execution as an ordered log, persisting one commit per
step, so that a mistaken step can be recovered mechanically. The engine
rewinds the persisted state with a git-style revert and then reverses external
effects by replaying each step's receipt through the tool's Undo mechanism.

## Reference implementation status

The reference implementation provides the typed checkpoint port, a Dolt
commit-per-step history, and the `Revert` operation together with receipt
persistence, reverse receipt walking, and the internal `checkpoint_rollback`
lifecycle tool. Test suites verify database rewind and both clean and
partially failed receipt reversals.

No production coding-agent profile routes validation failure into
`checkpoint_rollback`. The deployment-confirmation flow appears only in
Chapter 10's Approval Gate conformance/design material. Automatic coding
retry, gated deployment recovery, and generated compensation for mixed API
plans remain design-time intentions.

## Motivation

The motivation stems from the distinction between executions and append-only
logs. While logs merely record the past, executions must support traversal in
both directions. During forward traversal, the engine dispatches a tool,
records $(state, signal, tool, result)$ together with its receipt, commits the
record, and advances. During backward traversal, the engine reverts the state
to a target step and then feeds the restored results to each tool's `Undo`
method in reverse order. Because every entry contains the tool's
receipt—encapsulating all data required for reversal—a separate undo log
becomes unnecessary.

Agents inevitably make mistakes: a model may select the wrong tool, generate
faulty code, or misinterpret requirements. In the absence of rollback,
recovery forces a restart or a request for the model to self-correct, actions
that frequently compound errors. With rollback, the engine retracts the last N
steps—reverting the database and replaying receipts to reverse files and
resources—allowing execution to continue along a different path.

## Applicability

The Bidirectional Log pattern applies to agents whose actions generate
reversible side effects—such as file writes, state mutations, or resource
provisioning. It becomes valuable when recovery must be automated, when
speculative execution offers benefits, or when irreversible effects require
explicit logging. The pattern relies on versioned, incrementally persisted
state (for example, Dolt commits per step) and on receipts that enable undoing
external effects. Agents that produce no side effects or that operate with
inherently idempotent actions derive little advantage from this approach.

## Structure

A correct rollback isolates two concerns that share the same step index (see
Fig. 19). **Persisted state** comprises the resumable position—machine state,
signal, iteration, budget counters, folded conversation—and the ordered
execution log containing result digests and each tool's opaque receipt. The
system saves this state through a typed checkpoint port and versions it as a
commit-per-step using the Dolt backend. **External effects** denote changes to
the world outside the database (files, provisioned resources) that snapshots
do not capture; these effects are undone by replaying receipts through the
tool's `Undo`. Rewinding only the persisted state or only the external effects
yields an incomplete rollback. The process must revert the database to a
specific step and then walk the receipts back to that step.

### Participants

#### Receipt

The Receipt is an opaque string generated by a tool during `Execute`. It holds
the data needed to reverse the effect without referencing the original
object—such as a file path, prior content, a resource identifier, and a commit
hash. The originating tool defines the receipt's schema and is the sole entity
that decodes it; the engine and checkpoint adapters store the receipt verbatim
and do not interpret its contents.

#### Checkpoint port

The Checkpoint port is a typed, two-method persistence seam that provides
`Save(Position, Execution)` to record the resumable position and ordered log
as a single unit, and `Load` to restore them. Adapter implementations manage
serialization and storage. The default adapter uses Dolt, committing each
step, while `NoopCheckpoint` disables persistence without incurring overhead.

#### Execution

The Execution maintains an ordered dispatch log that records, for each
iteration, the state pair, signal, command, result digest, and receipt in
dispatch order. This structure enables forward inspection as well as reverse
traversal. The log is versioned as a Dolt commit-per-step history, providing a
detailed, traceable record of every step.

#### Lifecycle tool

Rollback, implemented as a dedicated lifecycle tool (`checkpoint_rollback`),
runs independently of the engine code and the domain machine. This separation
keeps the agent's actions distinct from its recovery mechanisms. The rollback
process proceeds in two stages: first, it executes Dolt's `Revert` to restore
the persisted state; second, it performs a reverse receipt walk. This approach
aligns with the reversibility tier described in Chapter 4.

| Reversibility tier | Undo behaviour |
|---|---|
| Noop | Read-only; empty receipt; skipped during rollback |
| Reversible | `Undo` decodes the receipt and restores the prior state |
| Compensatable | `Undo` derives a corrective action from the receipt, logs the difference |
| Irreversible | Skipped, logged as non-reversible |

## Collaborations

### The lifecycle tool

Rollback, invoked by a minimal lifecycle machine, traverses the run's
Execution and Dolt commit history. Fig. 20's state machine illustrates this
flow: starting in the **Reverting** state, the `Revert(run_id, step_index)`
operation rewinds the persisted state. The tool then walks entries in reverse,
labeling them **Undone** (reversible or compensatable) or **Skipped**
(irreversible, logged). Finally, the **Done** state returns a resumable
position.

![](figures/fig-21-rollback-lifecycle.png)

A lifecycle tool offers three advantages. First, its small size permits
exhaustive validation. Second, each rollback strategy can be encapsulated as
its own lifecycle tool. Third, it invokes `Undo` using only the execution and
commit history, never dispatching a domain tool; consequently, the domain
machine cannot progress inadvertently.

### Reversal by tier

Each reverted entry is handled according to its tier. **Reversible:** The
tool's `Undo` decodes the receipt and restores exactly what it changed—for
example, restoring file content or writing back a prior value.
**Compensatable:** When exact reversal is impossible, `Undo` derives a
corrective action from the receipt that restores an equivalent state, such as
deleting a newly created resource. The receipt supplies the resource
identifier, and any semantic differences—like a re-created resource receiving
a new ID—are documented. **Irreversible:** Effects that cannot be undone, such
as sent emails or published deployments, are skipped and logged explicitly in
the rollback report, including the tool, iteration, and reason. Because tier
classification occurs per entry, not globally, a single rollback can manage
mixed tiers.

## Consequences

### Benefits

#### Mechanical recovery

Reverting the database to a specific step and replaying receipts reverses
external effects deterministically, not probabilistically. Consequently, the
model resumes with a clean context that predates the error, free from
contamination by failed attempts.

#### Cheap exploration

The agent can execute entirely reversible plans speculatively and roll them
back automatically, guaranteeing that no residual artifacts remain.

#### Auditable irreversibility

Irreversible entries that are skipped appear in the rollback report, informing
operators about which effects remain persistent.

#### One persistence seam

Both Position and Execution use the same typed port into Dolt, guaranteeing
that the ordered, versioned history required for rollback and inspection
originates from a single commit-per-step store instead of a separate snapshot
format.

### Liabilities

#### Commit overhead

Committing each step consumes resources; therefore, persistence remains
optional, and `NoopCheckpoint` prevents disabled runs from incurring this
overhead.

#### An irreversibility floor

External effects produced by an irreversible tool cannot be undone by the
receipt walk; `Revert` rewinds only the database, leaving such effects
permanent.

#### Two-part coordination

Rewinding the persisted state and replaying receipts must target the same step
index, which simplifies the process compared with managing three separate
state layers. Nevertheless, the revert and receipt walk must still align at
the rollback's conclusion.

## Implementation

### Receipts and undo paths

**Live undo** runs within the same process. The tool remains in memory, allowing `Undo` to reverse the in-memory result directly, which improves speed and precision. **Post-restart undo** addresses process boundaries such as suspend and resume: `Load` restores the receipt-bearing result, and a new tool instance's `Undo` utilizes the receipt. State-mutating tools encode a receipt during `Execute`; read-only tools return an empty receipt and a no-op `Undo`. Enforcement is divided: the lifecycle validator checks for receipt *presence* on reversible state-mutating tools, while receipt *sufficiency*—the ability of the receipt to reverse the effect—is verified by the tool's round-trip test, not by the engine. Declaring a static tier enables planning, and the combination of presence checks and round-trip tests ensures honesty.

### Commit-per-step history

The Dolt backend commits each dispatched step, turning the execution log into
a versioned history instead of relying on periodic snapshots. `Save` records
the Position—machine state, signal, budget counters, and folded
conversation—along with the appended Execution entry as a single unit in one
commit. The port persists on every step, eliminating the need for a separate
snapshot policy. When suspending, the same port persists the state before
exit; `Load` then resumes by restoring the Position and Execution, re-entering
the machine at the restored position.

### Rollback: revert then replay

Rolling back to step $k$ involves two operations at the same index. First,
`Revert(run_id, k)` rewinds the persisted state—both Position and Execution—to
step $k$. Second, the lifecycle tool walks entries $k\!+\!1 \ldots n$ in
reverse, passing each entry's result to `Undo` while skipping and logging
irreversible entries in the rollback report. The process returns the machine
position at step $k$, allowing execution to resume as a *fresh continuation*
rather than a replay. Discarded entries remain only in the rollback report.

### Planning with reversibility

Dynamic planning strategies encompass **speculative execution** for wholly
reversible plans, **commitment phases** that employ reversible tools until
sufficient evidence triggers an irreversible commitment (guarded by a
confirmation state), and **saga-style compensation**
[@garcia-molina-sagas-1987] for mixed plans, wherein the lifecycle tool
derives the compensation order from the execution (the reverse of dispatch)
instead of hard-coding it.

## Relationships in the Pattern Language

Bidirectional Log integrates with the Machine Interpreter, requiring both the
Machine Interpreter and the Tool Contract for operation. Rollback depends on a
closed execution record, receipt-driven undo mechanisms at the tool level, and
explicit reversibility declarations. This integration underpins the Approval
Gate, which checkpoints before external decisions, and a fully implemented
Operator Port that exposes rollback and lifecycle operations directly through
the running machine. The system's complete grammar resides in
`pattern-language.yaml`.

## Design intent scenarios

**Automatic coding recovery.** A future coding profile could route validation failures to `checkpoint_rollback`, restore files using receipts, and retry with a clean context. Currently, no production profile implements this transition.

**Gated deployment recovery.** An deployed Approval Gate could establish a rollback floor before irreversible deployments and restore reversible pre-deployment effects after failed verifications. The shipped approval material serves as a conformance fixture rather than executing deployment or rollback of rejections.

**Generated API compensation.** A future planner may derive compensation orders for mixed resource creation and irreversible notifications from execution. No shipped profile currently demonstrates this orchestration.

## Known Uses

**Reference rollback mechanics.** The Dolt checkpoint adapter processes each dispatch, reverts the persisted Position and Execution to a designated step, and maintains receipts separately from the redacted tool output. The lifecycle receipt walker executes `Undo` in reverse sequence, handles previously classified failures, and logs skipped effects.

**Database transactions and rollback** [@gray-1978]. The canonical model of a durable, reversible sequence of operations with a commit boundary—where rollback restores the prior consistent state—serves as more than an analogue. The Dolt backend literally commits each step and reverts to a prior consistent state.

**Memento pattern** [@gamma-gof-1994]. Each tool encodes a Receipt during `Execute`, capturing an object's state for later restoration while concealing internal details. The tool defines the schema; the engine and Dolt adapter store the receipt opaquely, and only the originating tool decodes it on `Undo`. Thus, the pattern's encapsulation boundary is enforced rather than assumed.

**Event Sourcing** [@fowler-event-sourcing-2005] models state as a replayable, reversible event log, aligning with Dolt's commit-per-step execution. This approach provides a traversable log for executing operations forward and reverting them backward, mirroring Dolt's commit-per-step functionality.
